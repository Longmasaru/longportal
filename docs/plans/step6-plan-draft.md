## ユーザーの希望(2026-10-14 の会話より)

- 各自(別の社員も Claude で作っている)が作った**別々のプロジェクト**を、LONG PORTAL に**ひもづけたい**。
- DB は**共有**し、データを同じところに溜めたい。
- 大きすぎる木構造(全部を 1 つに抱え込む形)にすると、後で改修しにくい。**リレーショナルデータベースのように**組みたい。

## おすすめの形

「ポータルが土台、各アプリは別プロジェクト、DB は 1 つで部屋(スキーマ)を分ける」

```
                 ┌─────────────── Neon(1 つの DB) ───────────────┐
LONG PORTAL ───▶ │ core.*   社員・部署・拠点・ユーザー・権限・対象者   │ ← 正(マスタ)はここだけ
(ログインの窓口)  │   ↑ ID で参照(読み取りのみ)                      │
アプリ A ───────▶ │ app_a.*  アプリ A の表                            │
アプリ B ───────▶ │ app_b.*  アプリ B の表                            │
                 └──────────────────────────────────────────────┘
```

| 決めごと | 内容 | 理由 |
|---|---|---|
| ① DB は共有、部屋は分ける | 1 つの Neon に、アプリごとのスキーマ(`app_a.*` など)を作る | データが 1 か所に集まり、社員 ID で横断して集計できる |
| ② マスタは core だけ | 社員・部署などは各アプリで作らない。core の **ID を参照**する | 同じ社員が何か所にも登録される事態を防ぐ(リレーショナルの考え方) |
| ③ アプリ同士は直接つながない | アプリ A の表から、アプリ B の表を参照しない(core だけを参照) | 1 つのアプリを直しても、他のアプリが壊れない |
| ④ アプリごとに DB の鍵を分ける | アプリ専用の DB ログイン。自分の部屋は読み書き、core は読み取りのみ(公開用のビュー経由) | 1 つのアプリにミスや漏えいがあっても、社員マスタや他のアプリを壊せない |
| ⑤ 表の変更は各アプリが管理 | 各プロジェクトが、自分のスキーマの migration だけを持つ | 他のアプリの表を誤って変えない |
| ⑥ ログインはポータルに一本化 | ポータルでログイン → アプリへ移るときに、短時間だけ有効な「通行証」を渡す。アプリ側は検証し、利用可否はポータルの判定に従う | パスワードを各アプリで持たない。退職者や対象外の人をポータル側で一括して止められる |
| ⑦ 登録簿で束ねる | ポータルの `app_registry` に、各アプリの URL・表示名・対象者(Audience)を登録 | サイドバーに出す相手と、使える相手を、ポータルの画面で管理できる |

## 権限の分け方(2026-10-14 追記・運用しやすい形)

ユーザーの考える大枠は「全権限者 / 管理者(アプリ開発者)/ 一般利用者」。運用しやすくするため、**アプリ開発者とアプリ管理者を別の役割に分ける**(同じ人が両方を持ってもよい)。

| 役割 | 誰か(例) | できること | できないこと |
|---|---|---|---|
| ① 全権限者 | 長井さん(`system_admin`) | すべて。各アプリの開発者・管理者を指定する | (なし。最後の 1 人は外せない保護つき) |
| ② アプリ開発者 | アプリを作った社員 | 自分のアプリの**技術面**: 登録情報(URL など)の確認、DB の自分の部屋(スキーマ)の変更、動作確認 | 誰に使わせるかの決定、社員名簿の変更、他のアプリへの操作 |
| ③ アプリ管理者 | 現場の課長など、業務の責任者 | 自分のアプリの**運用面**: 利用者(Audience)の設定、そのアプリの権限(閲覧・承認など)を社員に渡す・外す | 社員名簿の変更、他のアプリの権限、全権限者の権限 |
| ④ 一般利用者 | 社員 | 対象になっているアプリを使う | 管理画面 |

### 分ける理由

- 作る人(技術)と、使わせる相手を決める人(業務)は、多くの場合ちがう。開発者が異動・退職しても、アプリの運用は止まらない。
- 開発者に「誰でも使わせられる」力を持たせないので、テスト中のアプリを誤って全社に公開する事故を防げる。
- 小さなアプリでは、同じ人に ② と ③ の両方を渡せば、手間は増えない。

### 実現のしかた

- 新しいアプリは作らず、**ポータルの管理画面の機能**として持たせる(`/admin/apps` の中に「開発者」「管理者」の指定欄を設ける)。
- アプリごとに、開発者・管理者の割当を持つ。仕組みは、手順 4 のロール割当(スコープつき)を「アプリ」の軸に広げる形を基本に検討する。
- アプリ管理者が渡せるのは、**そのアプリの manifest に定義された権限だけ**。core の権限(社員・ロール・Audience の管理など)は渡せない。
- 誰が誰に何を渡したか・外したかは、監査ログに残す。
- 全権限者は、いつでも各アプリの割当を確認・取り消せる。

```
長井さん(全権限者)
 ├─ アプリ A ─ 開発者: Bさん / 管理者: Dさん(現場の課長)─→ Dさんがアプリ A の権限を社員に配る
 └─ アプリ B ─ 開発者: Cさん / 管理者: Cさん(兼任)    ─→ Cさんがアプリ B の権限を社員に配る
```

## 用語メモ

- **マスタ**: 社員・部署・拠点・役職・雇用区分など、みんなが共通で使う基本の名簿や一覧表。ポータル(core)に 1 つだけ置き、各アプリは番号(ID)で指す。
- **スキーマ**: 1 つの DB の中の「部屋」。表をアプリごとにまとめる単位。
- **マスタ**: 社員・部署など、みんなが共通で使う基本の名簿。
- **ID で参照**: 名前ではなく、変わらない番号で相手の行を指すこと(名前が変わっても、つながりが切れない)。
- **ビュー**: 表の一部の列だけを見せる「窓」。見せてよい情報だけを公開できる。
- **migration**: 表の形を変える手順を、記録として残したもの。
- **SSO(シングルサインオン)**: 1 回のログインで、複数のアプリを使えるようにする仕組み。
