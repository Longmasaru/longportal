# ポータル側からの回答

(2026-10-14、LONG PORTAL のリポジトリを調べて回答。対象: 老川さんの新しいアプリ「注文書CSV変換」)

## 最初に知っておいてほしいこと(前提の訂正)

- 「各アプリは別プロジェクト」という構成は、**方針として検討中で、まだ実装されていない**。ポータルにつながっている別プロジェクトのアプリは、まだ 1 つもない。
- このため、別プロジェクトのアプリが**ポータルのログインを使う仕組み(SSO)は、まだない**。ポータル側で、次の作業(手順 6)として作る予定。
- ポータルにあるのは、ログイン、初回のパスワード変更、管理画面(社員・組織・ロール・対象者・監査ログ)。「マイページ」はまだない。
- 注文書CSV変換は、別プロジェクトとしてつなぐ**最初のアプリ**になる見込み。ポータル側の仕組みは、このアプリと一緒に固める。

## 1. 技術構成

**結論: 同じ構成にそろえる。**

| 項目 | ポータルの構成 |
|---|---|
| フレームワーク | Next.js **16.3.8**(App Router)。ただし学習データの Next.js とは仕様が違うので、`node_modules/next/dist/docs/` を確認しながら書く |
| 言語 | TypeScript 5.9.3 |
| React | 19.2.8 |
| スタイル | Tailwind CSS 4.3.3 と、ロングのデザインシステム(配色・書体)。画面のルート文字サイズは 16px 固定 |
| 入力の検証 | zod 4.6.5 |
| DB | PostgreSQL(Neon)、`pg` 8.23.1、Drizzle ORM 0.45.3、drizzle-kit 0.31.11 |
| Node / npm | Node **24.x**、npm 11.x(`engines`、`.nvmrc`、`.npmrc` の `engine-strict=true` で固定) |
| 依存の書き方 | `^` を付けず、版を完全に固定する |
| 公開 | Vercel。関数の地域は `vercel.json` で **sin1**(シンガポール。DB と同じ) |

このアプリで追加するライブラリについての注意:

- **SheetJS(xlsx)**: npm の `xlsx` パッケージは古い版で止まっていて、既知の脆弱性がある。公式の配布元(cdn.sheetjs.com の tgz)の最新版を、版を固定して入れる。
- **pdf.js**: `pdfjs-dist` を使う。worker の読み込み方は、Next.js 16 のドキュメントで確認する。
- **encoding.js**: npm 名は `encoding-japanese`。Shift-JIS の出力に使う。

## 2. 認証の仕組みと、別プロジェクトからの確認方法

**結論: いまは、別プロジェクトから確認する方法はない(未定)。ポータル側で SSO を作るまで、本番公開は待つ。**

ポータル内部の仕組み(参考):

| 項目 | 内容 |
|---|---|
| ライブラリ | Auth.js v5(`next-auth` 5.0.0-beta.32)。Credentials(ID とパスワード)、`bcryptjs` |
| セッション | JWT(署名付きのクッキー)。中身は `userId` だけ。権限や在籍状態は JWT に入れない |
| 本当の判定 | 毎回 DB を見る。「アカウントが有効か」「入社日前・退職日の翌日以降ではないか」「権限」を、リクエストのたびに確認する(deny by default = 迷ったら拒否) |
| 入口の確認 | `src/proxy.ts`(ログイン済みかどうかの大まかな確認だけ) |
| 参考の場所 | `src/modules/core/auth/auth.ts`、`auth.config.ts`、`src/modules/core/access/actor.ts`(`resolveActor`)、`evaluate.ts`、`guards.ts` |

別プロジェクトのアプリ向けの予定(案。ポータル側で作る):

1. 社員はポータルでログインする。
2. ポータルのメニューからアプリへ移るとき、ポータルが**短時間だけ有効な署名付きの通行証**を発行する。
3. アプリは通行証を検証し、「誰か(user の ID)」と「このアプリを使ってよいか」「アプリ内の権限」を受け取って、アプリ自身のセッションを作る。
4. アプリ側は、パスワードを持たない。退職や対象外の人は、ポータル側でまとめて止まる。

**アプリ側で自前のログインを作らないこと。** 検証に使う部品と手順は、ポータル側で用意して渡す。

## 3. アプリをポータルにつなぐ方法

**結論: 別ドメイン(別の Vercel プロジェクト)で公開し、ポータルの「アプリ登録簿」に登録してメニューに出す。**

- ポータルの配下のパスには置かない。
- ポータルの管理画面に、アプリの登録簿(`core.app_registry`。URL、表示名、アイコン、使える人の範囲)を作る予定(未実装)。
- 使える人の範囲は、ポータルの「Audience(対象者の条件。部署・拠点・役職などで指定)」で決める。メニューに出す相手と、実際に使える相手は同じ判定にする。
- **既存アプリの例はない**(サイドバーのアプリ項目は、いまは見本の表示)。

## 4. ひな形・参考にすべき既存アプリ

**結論: ひな形はまだない(未定)。ポータル側で、アプリ作成者向けの手順書を用意する予定。**

それまでの参考:

- 設定ファイル(`tsconfig.json`、`eslint.config.mjs`、`postcss.config.mjs`、`.nvmrc`、`.npmrc`)は、ポータルと同じものを使う。必要なら上司から受け取る(ポータルのリポジトリは非公開)。
- 見た目は、ロングのデザインシステム(ポータルの `docs/design-system-long-kanazawa.md` と `src/app/globals.css`)に合わせる。

## 5. Neon の使い方

**結論: DB はポータルと共有する。アプリごとに「スキーマ(DB の中の部屋)」と「専用の DB ユーザー」を分ける予定(準備中)。第 1 段階では DB を使わないので、まだ不要。**

| 項目 | 内容 |
|---|---|
| Neon の project | ポータルと同じ 1 つ。ブランチは `development`(開発)と `production`(本番) |
| 分け方(予定) | アプリ専用のスキーマ(名前は未定。例: `order_csv`)。アプリ専用の DB ユーザーは、自分のスキーマを読み書きでき、ポータルの社員情報などは**公開用のビューから読むだけ** |
| 守ること | 社員・部署などの名簿は、アプリで作らない(ポータルの ID で参照する)。他のアプリの表を参照しない |
| ORM / migration | Drizzle ORM。`pgSchema("スキーマ名")` で表を定義し、`drizzle-kit generate` → `drizzle-kit migrate` の正式な migration で変える。起動時に表を自動で作る方式は使わない |
| 環境変数 | `DATABASE_URL`(Neon の pooled。ホスト名に `-pooler` が付く。アプリの実行用)、`DATABASE_URL_UNPOOLED`(direct。migration 用。手元だけで使い、Vercel には置かない)。手元は `.env.local`(開発用のブランチだけ)。雛形は `.env.example` |
| 本番の接続先 | Vercel の環境変数に「Sensitive」で登録する。本番の接続文字列は手元に置かない |
| 地域 | Neon は AWS のシンガポール(ap-southeast-1) |

## 6. 進め方の案について(合わない点・気をつける点)

**結論: 3 段階の進め方は、ポータルの方針と合っている。特に、第 1 段階で注文書をサーバーに送らない点はとても良い。** 気をつける点は次のとおり。

1. **第 1 段階でも、ログインなしで本番公開しない。** 取引先名や変換の規則がコードに入るため、URL を知っている人が誰でも開ける状態は避ける。開発は手元で進め、本番公開はポータルの SSO ができてからにする。
2. **変換履歴の「誰が」は、名前ではなくポータルの user の ID で持つ。** 表示するときに、ポータルの公開用ビューから名前を引く。
3. **取引先(高井、USG など)と品番対応表は、アプリのスキーマに置いてよい。** 将来、他のアプリでも取引先を使うことになったら、ポータル側の共通の名簿に移すことを検討する。
4. **USG の重複チェック**: 第 2 段階の始めに、`\\will-server` の過去の CSV から客先注番を 1 回だけ Neon に取り込む。そのあとは、変換のたびに Neon に記録する。
5. **第 3 段階(Claude API)**: FAX の画像を社外の API に送ることになる。送ってよいかは、上司の承認が必要。API キーはサーバー側の環境変数だけに置き、ブラウザに出さない。画像を保存する場合は、ポータルと同じ Cloudflare R2 の仕組み(署名付き URL)を使う。
6. **Vercel の関数の本文は 4.5MB まで。** 第 1 段階はブラウザ内で処理するので関係ない。第 3 段階でファイルをサーバーに送るときは、R2 への直接アップロードにする。
7. **文字コード**: Shift-JIS で表せない文字(一部の旧字体や機種依存文字)が入ったときの扱いを決めておく。黙って「?」にしない。

## 7. このアプリを使える人の範囲

**結論: 全社員には出さない。担当者だけ。**(上司の回答)

- ポータルの Audience(対象者の条件)で、担当者だけに絞る。具体的な条件(どの部署・拠点か、個人か)は、ポータルにつなぐときに上司が設定する。
- アプリ側でも、ポータルから受け取った「このアプリを使ってよいか」の判定が NG なら、画面を出さない(URL を直接開いても使えないようにする)。

## 8. 第 2 段階で、取引先名・客先注番・変換履歴を Neon に保存してよいか

**結論: 保存してよい。**(上司の回答)

- 保存先は、5 のとおり、アプリ専用のスキーマ。
- 注文書の原本(ファイルそのもの)は、必要になるまで保存しない(第 1 段階の方針どおり、変換はブラウザ内)。保存したくなったら、先に上司に相談する。

## 9. 老川さんの GitHub と Vercel での権限

**結論: GitHub はこのアプリのリポジトリだけに招待。変更はプルリクエストで上司の確認を通す。Vercel は当面、上司が管理する。**(上司の回答)

- GitHub: 上司がリポジトリを作り、老川さんを招待する。ポータル本体のリポジトリには招待しない(必要な設定ファイルや手順書は、上司から渡す)。
- 作業の流れ: ブランチを作る → プルリクエストを出す → 上司が確認して `main` に入れる。`main` に入ると Vercel が自動で本番に出すので、`main` へ直接 push しない。
- Vercel: プロジェクトの作成、環境変数(DB の接続先など)の登録、ドメインの設定は上司が行う。老川さんは、プルリクエストごとのプレビュー URL で動きを確認する。
